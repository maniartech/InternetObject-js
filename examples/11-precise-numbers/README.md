# Precise numbers

```js
0.1 + 0.2   // 0.30000000000000004
```

Every language with IEEE floats does this, and JSON has exactly one number type: a float. For money, that is not a quirk — it is a bug waiting for a large enough invoice.

## `decimal` — exact, and it keeps its scale

Write `19.99m`. The `m` suffix says decimal, and you get an exact value rather than the nearest float.

Scale is part of the value: **`1.50m` is not `1.5m`**. A price list that says `1.50` still says `1.50` after a round trip, which matters when a human reads the output.

## `bigint` — every digit

JavaScript numbers are exact only up to `9007199254740991`. Past that, digits are silently lost:

```js
JSON.parse('9007199254740993')   // 9007199254740992  — wrong by one
```

Write `9007199254740993n` and every digit survives. Snowflake ids, database keys, anything generated by a system that does not care about your float precision.

## The marker is the point

`m` and `n` are not decoration. They are how the document **states which kind of number it means**, so the reader never has to guess:

| Written | You get |
| ------- | ------- |
| `12` | `number` |
| `12m` | `Decimal` |
| `12n` | `bigint` |

A document that means money says so, and any implementation in any language reads it the same way. That is the part JSON cannot do at all — there, `19.99` is just a float and the meaning lives in documentation nobody reads.
